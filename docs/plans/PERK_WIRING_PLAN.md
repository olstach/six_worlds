# Wiring the perks — implementation guide

Hand this file to a session cold. It is meant to be self-contained: what exists,
what is broken, what to build, in what order, and how to know a batch is done.
The per-perk inventory is `docs/review/PERK_FIXES.md`, regenerated by
`python3 tools/export_perk_fix_list.py`.

Last verified against the tree on 2026-09-09. Line numbers drift; function names
do not, so grep for those.

---

## 1. The situation in one page

603 perks. Each is `{name, description, flavor, is_mantra}` plus gating fields.
**The mechanics live in the English `description` and nowhere else.**

Three things are true and each changes what you should do:

**a. 138 perks work, through hand-written `if PerkSystem.has_perk(...)` checks
scattered through combat code.** They function. But each is bespoke, which is
exactly why the other 465 were never done — every one needs its own `if`.

**b. There is a complete, tested active-perk pipeline with no data in it.**
`scripts/combat/combat_arena.gd` builds a skill button for any perk whose
description begins with `Active`, handles stamina, cooldowns, weapon
requirements and targeting, and `CombatManager.use_active_skill()` dispatches
**44 implemented effect types**. Not one perk in `perks.json` carries a
`combat_data` block, so the button appears greyed with *"Skill not yet
implemented"* and all of it goes unused. This is the single biggest and cheapest
win available, and an earlier version of this document under-reported it as
"8 effect types", which is why it was mis-prioritised.

**c. Passive perks now have a typed home.** `resources/data/perk_effects.json`
declares 17 effect types and 22 conditions; a perk carries an `effects` array.
`stat`, `resistance`, `status_resistance`, `immunity` and `note` are
implemented. 8 perks are migrated.

### Two data fields, deliberately kept apart

| Field | For | Read by | State |
|---|---|---|---|
| `combat_data` | Active perks — the player presses a button | `combat_arena.gd` → `CombatManager.use_active_skill()` | 44 effect types work, 0 perks use it |
| `effects` | Everything passive or conditional | `PerkSystem` → `CharacterSystem` / `CombatManager` | 5 of 17 types work, 8 perks use it |

**Do not merge them.** `combat_data` is working code with a rich vocabulary and
an AI scorer. Folding it into the registry for tidiness would break a working
system to make a document neater.

### Why "batch by system" and not by anything else

A batch is finishable exactly when **it is one hook**. Grouping by perk count,
skill, or condition gives you batches that cannot be completed, because half the
perks in them need a hook that does not exist yet. `PERK_FIXES.md` is grouped by
the system that owns the hook for that reason.

## 2. Batch 0 — verify the stat pipeline (gate, do this first)

The stat pipeline landed in commit `ae60452` and **has never been executed** —
there was no Godot in the environment that wrote it. Everything below assumes it
works. Verify before building on it.

Open the project and read the startup console:

```
PerkSystem initialized: 549 skill perks, 54 cross perks, 40 base bonus tables, 17 effect types
CharacterSystem initialized with ... 44 stat keys
```

`44 stat keys` missing or zero means `stat_keys.json` did not load, and **every
percentage silently vanishes** — modifiers route through `canonical_stat()`,
which returns `""` and drops them with a single warning. That is the failure
mode to watch for: it is quiet, not loud.

Then make a character with Swords 5 and a 12-damage weapon:

| Stat | Expect | If you see this instead, the percentage stage is not running |
|---|---:|---|
| damage | 25 | 117 |
| armor (Armor 4) | 12 | 58 |
| hit chance vs dodge 14 | 86% | 95% |

Constructs that have never run in an engine and are worth a second look:

- `const STATUS_CATEGORIES := {...}` declared **inside**
  `CombatManager._check_typed_status_immunity` — there is precedent in that file
  for a function-local `const` dictionary, but with `=` rather than `:=`.
- The three-pool loop in `EnemySystem._calculate_derived_stats`: a backslash
  line continuation, and `var max_key := "max_" + pool` where `pool` comes from
  an untyped array literal.
- `String.trim_suffix()` and `Dictionary.get()` on a `const` in
  `main_menu.gd::_format_bonus_preview`.

## 3. Batch 1 — actives (109 perks)

**Do this first.** It is pure data authoring against working code, every perk is
verifiable in-game the moment you write it, and it touches nothing else.

### How the pipeline finds a perk

`combat_arena.gd::_get_active_skills()` collects any owned perk whose
**description begins with the literal string `Active`**. No flag needed. The
button already appears; it is greyed until `combat_data` is non-empty.

### The shape

```json
"measured_strike": {
  "name": "Measured Strike",
  "skill": "swords",
  "required_level": 2,
  "description": "Active (3 Stamina). Make an attack with +20% accuracy. On hit, gain +15% Armor for 1 turn.",
  "combat_data": {
    "effect": "attack_with_bonus",
    "targeting": "single",
    "stamina_cost": 3,
    "range": 1,
    "accuracy_bonus": 20,
    "buffs": [{"stat": "armor", "value": 15, "duration": 1}]
  }
}
```

`targeting` is `self`, `single` or `aoe`. `buffs` entries are
`{stat, value, duration}`; `statuses` entries are `{status, duration, value}`.
`debuffs` entries have the same shape as `buffs` and **the value is negated for
you** — write `{"stat": "dodge", "value": 15}` to impose −15, not −15 itself.
Stat names in `buffs` should come from `stat_keys.json`; status names must exist
in `statuses.json`.

### The 44 effect types

Grep `func use_active_skill` in `scripts/autoload/combat_manager.gd` for the
authoritative `match` — each arm names its `_resolve_*` function, and reading
that function tells you exactly which `combat_data` keys it consumes.

```
attack_with_bonus  dash_attack        aoe_attack        aoe_damage_and_status
debuff_target      debuff_enemies     mark_target       aggro_aura
buff_self          buff_ally          buff_allies       buff_allies_debuff_enemies
share_buffs        double_buffs       cleanse_and_buff  dispel_and_invert
stance             heal_self          revive            restore_stamina
restore_armor      bonus_movement     grant_extra_action retreat
teleport           mass_teleport      enter_stealth     force_miss
grapple            guard_ally         destroy_obstacle  create_terrain
create_images      summon_aura        place_trap        steal_item
imbued_attack      overcast           consume_charm     recruit_or_pacify
choose_one         examine            chod_offering     throw_phurba
```

Parameters for the common ones, read out of their resolvers:

| Effect | Keys it reads |
|---|---|
| `attack_with_bonus` | `range`, `damage_bonus_pct`, `accuracy_bonus`, `armor_ignore_pct`, `resist_ignore_pct`, `ignore_dodge`, `refund_on_kill` |
| `dash_attack` | `dash_range` (plus the attack keys above) |
| `aoe_attack` | `range`, `aoe_radius`, `damage_pct` |
| `buff_self` / `stance` | `buffs[]`, `statuses[]` |
| `debuff_target` | `range`, `deals_damage`, `debuffs[]`, `statuses[]` |
| `heal_self` | `heal_value`, `scale_stat`, `stamina_restore_pct` |
| `teleport` | `teleport_range`, `buffs[]` |

Universal: `stamina_cost`, `cooldown`, `once_per_turn`, `once_per_combat`,
`free_action`.

### Fix this bug while you are in there

**The button and the executor read stamina cost from different places.** The
button label and its greying use `_parse_stamina_cost(description)` — a regex
for `(N Stamina)` in the prose. The executor
(`CombatManager.use_active_skill`) charges `combat_data.stamina_cost`. If they
disagree the UI lies, and **only 34 of the 109 actives state a cost in their
description**, so 75 will show "no cost" while being charged.

Fix in `combat_arena.gd::_get_active_skills()`: prefer
`combat_data.stamina_cost` and fall back to the parse.

### Order within the batch

Roughly, by how many perks share an effect type: `buff_self` (~34),
`aoe_attack` (~18), `stance` (~8), then the long tail. Do one effect type at a
time and playtest it before starting the next.

### Done when

Every perk whose description begins with `Active` carries a `combat_data` block,
no button in combat reads *"Skill not yet implemented"*, and
`python3 tools/export_perk_fix_list.py` reports 0 under `actives`.

## 4. Batch 2 — combat stats and the condition evaluator (75 perks)

The batch that pays for itself: **the conditions already exist, inline, 35+
times over.** `while wielding a sword` is written out as
`get_equipped_weapon().get("type","") == "sword"` in 28 places, `_unit_is_unarmored`
at 6 call sites, and the adjacency helpers at 27. Writing the evaluator is mostly
deleting those.

### Prerequisite: two accessors have no perk hook at all

`CombatUnit.get_accuracy()` and `get_spellpower()` never call
`CombatManager.get_passive_perk_stat_bonus()`, while `get_dodge`, `get_armor`,
`get_movement`, `get_initiative` and `get_crit_chance` all do. **No accuracy or
spellpower perk can work today, hand-wired or not.** Add the hook to both before
anything else in this batch.

### Build

1. `PerkSystem.evaluate_condition(character, unit, condition, effect) -> bool`,
   covering the conditions in `perk_effects.json`. Start with `wielding`,
   `armor_class`, `adjacent_allies`, `adjacent_enemies` — that is most of the
   batch.
2. `PerkSystem.get_conditional_stat_modifiers(character, unit, stat)`, mirroring
   `get_passive_stat_modifiers()` but running the evaluator.
3. Call it from `get_passive_perk_stat_bonus()` alongside the existing
   hand-written arms.
4. Migrate the 33 hand-wired perks in this group to `effects` blocks and **delete
   their `if` statements**. Net negative lines.

`stat_conversion` is declared in the registry but not implemented, and it is
what Parry and Improved Parry actually do — a share of one stat added to
another, which has to be recomputed rather than folded into derived stats once.
Implement it here.

### Done when

The condition evaluator serves the four common conditions, the hand-written
copies are gone, and `PERK_FIXES.md` shows `combat_stats` shrinking.

## 6. Rules that apply to every batch

**Never invent a number.** If a description says "a chance to stun" without
saying how much, that is a balance decision for Olaf, not a gap to fill. Collect
them and ask. This is the same wall the spell backlog hit: 299 of its legacy
keys are a bare `true`, and migrating one means choosing a number it never
carried.

**Never wire a perk twice.** A perk that carries a typed `effects` entry *and* a
hand-written `has_perk` check applies both. Stone Adept did exactly this — +10%
Armor in data and +10% Armor in `CombatManager`, the second computed from the
already-boosted value. `validate_data.py` now treats that as an error for
implemented effect types. When you migrate a hand-wired perk, **delete its
`if`.**

**Names must point at something real.** A status name that matches nothing
silently never fires. Pain Is Just Information resisted `"exhausted"`, which is
not a status this game has, so a third of the perk did nothing for as long as it
existed. The validator checks status names and summon templates inside effects
now; keep it that way.

**Run the gate.** `python3 tools/validate_data.py` must exit 0 before any
commit. It checks effect types, conditions, required params, stat names against
`stat_keys.json`, perk prerequisites, status names, and double-application.

**Regenerate the inventory.** `python3 tools/export_perk_fix_list.py` after each
batch — a perk drops out when it is wired, so the counts are the progress bar.

**Record authored prose.** Anything written for Olaf to review — descriptions,
flavour, invented mechanics — goes in `EDIT_LATER.md` with a note on what is
Claude's and what is his.

## 7. Verifying a batch

Order matters, because the cheap checks catch most of it:

1. `python3 tools/validate_data.py` — exits 0.
2. Load the project; read the console for parse errors and the initialisation
   counts.
3. In combat, look at the character sheet: are the numbers plausible? The
   pipeline is quiet when it fails.
4. Play the specific perks. For actives this is direct — press the button. For
   passives, compare a character with and without the perk.
5. `python3 tools/export_perk_fix_list.py` — the batch's count should be 0.
